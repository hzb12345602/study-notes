# 26.9.27 PC/嵌入式：内存与寄存器

> 学习笔记。核心问题：芯片内存的使用和管理，以及它和寄存器的核心差别。
> 起点：聊完底层硬件、上层软件、通信协议，想深入核心底层——芯片内存到底怎么用、怎么管。

## 一、物理本质：它们到底是什么

### 寄存器 (Register)

CPU 核心**内部**的、与 ALU 直接相连的极快存储单元。

| 特征 | 说明 |
| :--- | :--- |
| 位置 | CPU 核心内部，距 ALU 最近（纳米级） |
| 速度 | 与 CPU 同频，单周期读写（~0.3ns @ 3GHz） |
| 容量 | 几十~几百个，每个 32/64 位 |
| 寻址 | 由指令直接编码（`add r1, r2, r3`） |
| 实现 | 触发器（Flip-Flop）或锁存器（Latch） |
| 功耗 | 极高（一直通电保持状态） |

关键理解：**寄存器不是内存**。它是 ALU 的直接操作数来源和结果去向。Load-Store 架构（RISC-V/ARM）里，ALU 只能碰寄存器，不能碰内存。

### 内存 (RAM)

CPU **外部**的、通过总线访问的大容量存储阵列。

| 特征 | 说明 |
| :--- | :--- |
| 位置 | 芯片内（SRAM）或芯片外（DRAM） |
| 速度 | L1 ~4 周期，L2 ~12 周期，DRAM ~200 周期 |
| 容量 | KB~GB |
| 寻址 | 通过地址总线，需要计算地址 |
| 实现 | SRAM（6 晶体管/位）或 DRAM（1 管+1 电容/位） |
| 功耗 | 相对低（DRAM 刷新有额外功耗） |

关键理解：内存是一个**巨大的字节数组**，每个字节有地址，CPU 通过 Load/Store 访问。

## 二、核心差别：一张表

| 维度 | 寄存器 | 内存 |
| :--- | :--- | :--- |
| 物理位置 | 核心内部 | 核心外部 |
| 访问速度 | 1 周期 | 4~200+ 周期 |
| 容量 | 几十~几百个 | KB~GB |
| 寻址方式 | 指令编码 | 地址总线 |
| 访问指令 | ALU 直接操作 | Load/Store |
| 生命周期 | 指令级（临时） | 程序级（持久） |
| 编译器角色 | 分配目标 | 溢出（Spill）目标 |
| 程序员可见性 | 汇编可见，C/C++ 不可见 | 通过指针可见 |
| 功耗/位 | 极高 | 较低 |
| 成本/位 | 极高 | 低 |

> 寄存器是 CPU 的**工作台**，内存是**仓库**。ALU 只能在工作台上干活，仓库的东西必须先搬到工作台。

## 三、内存层次结构：为什么需要 Cache

既然寄存器快、内存慢，全放寄存器不就行了？**不行**——寄存器太少（RISC-V 只有 32 个）、太贵、程序数据量远大于寄存器容量。于是有了层次结构：

```
           容量        速度       成本/位
寄存器     几十个      1周期       极高
L1 Cache  32~64KB     4周期       高
L2 Cache  256KB~1MB   12周期      中
L3 Cache  几MB~几十MB 40周期      低
DRAM      几GB~几TB   200周期     极低
SSD/HDD   几TB        微秒~毫秒   最低
```

核心思想：用**局部性原理**让大部分访问落在快速层级。

- **时间局部性**：刚访问的数据，很可能马上再访问（循环变量）
- **空间局部性**：刚访问的数据，旁边的很可能马上访问（数组遍历）

Cache 自动把内存搬到靠近 CPU 的地方，程序员不必显式管理。

## 四、程序在内存里的分段

```
+------------------+ 低地址
|  .text 代码段     | 机器指令，只读
+------------------+
|  .data 数据段     | 已初始化全局/静态变量
+------------------+
|  .bss 段         | 未初始化全局/静态，清零
+------------------+
|  Heap 堆         | malloc/new，向高地址增长
+------------------+
|  Stack 栈        | 局部变量、调用帧，向低地址增长
+------------------+ 高地址
```

- **嵌入式/DSP**：布局由链接器命令文件（.cmd）显式控制——.text 放 Flash 哪个地址、.data 放 RAM 哪个地址、栈堆多大
- **PC**：操作系统用虚拟内存管理，程序员不关心物理地址

## 五、寄存器分配：编译器的核心难题

程序变量无限，寄存器只有 32 个，怎么分？核心算法是**图着色 (Graph Coloring)**：

1. **活跃变量分析**：判断每个变量在哪还"活着"（后面还会用）
2. **构建冲突图**：两个变量同时活跃就连一条边
3. **K 着色**：K = 物理寄存器数，有边的不能同色
4. 染不上色 → **溢出 (Spill)** 到栈

这是 **NP 完全问题**，实际用 Chaitin-Briggs 启发式。RISC-V 细节：32 个寄存器里 `zero`/`sp`/`ra`/`gp`/`tp` 有特殊用途，实际可用更少；ABI 规定 caller-saved / callee-saved，直接影响分配策略。

## 六、内存管理：裸机 vs 操作系统

### 裸机（DSP/嵌入式）

无 OS，直接管理物理内存：手动设栈指针、通常不用堆（禁止动态分配）、外设寄存器映射到物理地址用 volatile 访问。

```c
volatile uint32_t *adcReg = (volatile uint32_t *)0x4000;
uint32_t result = *adcReg;  // 直接读物理地址
```

### 有操作系统（PC/服务器）

虚拟内存：每进程独立虚拟地址空间，MMU 翻译，页表存映射，缺页异常触发磁盘加载。代价是引入 TLB Miss、Page Fault 等新问题。

## 七、编程语言视角

| 语言 | 寄存器可见性 | 内存管理方式 |
| :--- | :--- | :--- |
| 汇编 | 完全可见，手动分配 | 手动管理地址 |
| C | 不可见，编译器分配 | 手动 malloc/free |
| C++ | 不可见，编译器分配 | RAII、智能指针 |
| Rust | 不可见，编译器分配 | 所有权系统，编译期检查 |
| Java/Python | 完全不可见 | GC 自动管理 |

C/C++ 的两个误区：
- 以为 `int x = 5;` 的 x 一定在内存——实际可能在寄存器，或被优化掉（常量传播）
- 以为 volatile 是"从内存读"——实际是"不要优化掉这个访问"

## 八、DSP 特殊性（TMS320F28004x）

| 特性 | 说明 |
| :--- | :--- |
| 统一寻址 | 程序和数据共享同一地址空间（改进哈佛架构） |
| 多总线 | 程序读/数据读/数据写独立总线，可并行 |
| Flash vs RAM | 代码默认 Flash，需搬运到 RAM 才能全速运行 |
| 等待状态 | Flash 需 RWAIT，RAM 不需要 |
| CLA 独立内存 | CLA 有自己可访问的 RAM 块（LSx） |
| DMA | 不经 CPU，直接内存↔外设搬数据 |
| 外设寄存器 | 映射到内存地址空间，volatile 访问 |

关键：DSP 内存管理是**显式**的，必须通过 .cmd 文件告诉编译器代码放哪、栈堆多大、外设地址。

## 九、一句话总结

> 寄存器是 CPU 的**手**，内存是**仓库**，Cache 是传送带。编译器的核心任务，就是决定什么时候用手、什么时候去仓库取、什么时候把东西放回仓库。

**四个知识点的交汇处**（Load-Store 架构 + 编译器寄存器分配 + DSP 显式内存管理 + CPU/GPU 性能分析），就是"芯片内存的使用和管理"——已经站在一个很高的视角上了。
