# 26.10.21 CUDA 概念复习：Block / Warp / Tile / SM

> 学习笔记。核心主线：分清 **软件抽象 / 硬件实体 / 数据策略** 三类东西。
> 起点问题：block 在软件上是个名字、背后绑定硬件？tile 是数据搬运优化策略？写代码就是开 kernel、按硬件分 block、写 tile？——方向对，边界要拆干净。

## 一、先一句话归类（最重要的框架）

| 类型 | 成员 |
| :--- | :--- |
| **软件抽象层** | Grid、Block、ThreadIdx（你代码里写的） |
| **硬件实体** | SM、Warp（你控制不了，硬件自动管理） |
| **数据策略** | Tile（纯软件优化手段，与硬件调度无关） |

## 二、Block：软件分组，但绑定硬件调度

- Block 是你代码里 `<<<grid, block>>>` 指定、`blockIdx`/`threadIdx` 访问的**软件分组**
- 硬件上：SM（流式多处理器）负责调度、承载 Block；**一个 Block 必须完整跑在同一个 SM 上，不能跨 SM 拆分**
- 软件层面：你随便设 block 大小 16×16、32×8
- 硬件约束：block 上限 1024 线程；同一 block 所有线程共享同一块 Shared Memory，可用 `__syncthreads()` 同步

## 三、Warp：纯硬件执行单元（重点）

> **Warp 是硬件真正调度、发射指令的最小单位。软件层面不能直接创建 warp，一般看不见 warp ID。**

- 几乎所有 NVIDIA GPU：**一个 warp 固定 = 32 个连续 thread**
- 同一个 warp 里 32 个线程**取同一条指令**（SIMT：单指令多线程）
- SM 里硬件**按 warp** 取指、发射、流水线执行——不是按 block、不是按 thread
- Block 只是一堆 thread 的集合，硬件自动打包成若干 warp：
  - Block 256 线程 → 256 / 32 = **8 个 warp**
  - Block 128 线程 → 4 个 warp

**SIMT 和 CPU SIMD 的差别**：warp 内线程可以分支（if-else），代价是**分支发散（warp divergence）**——同一 warp 里一部分走 if、一部分走 else，硬件会串行跑两条分支，性能直接掉下去。

## 四、Tile：纯数据优化策略

- Tile 和硬件调度单元**没有强制绑定**，只是工程习惯上一个 Block 处理一个 Tile
- Tile 关心：这块数据多大、什么时候从全局显存搬到 shared、什么时候复用
- 完全可以一个 Block 处理多个 Tile，或多个 Block 协作处理一个超大 Tile（少这么写，同步不好控制）
- Tile 不改变 Grid/Block/Thread 的硬件调度规则

## 五、层级总览（硬件 + 软件对照）

```
Grid（软件，所有 block 集合）
├─ Block（软件线程组，绑定到单个 SM）
   ├─ Warp（硬件调度最小单元，32 thread）
      ├─ Thread（软件单线程，你写的 threadIdx）
```

- **SM**（硬件，GPU 核心集群）：可同时驻留很多 Block、很多 warp，靠 **warp 切换掩盖显存延迟**（GPU 靠多线程藏延迟的本质）
- **Shared Memory**：属于 Block，在 SM 片上；同一 block 内所有 warp 共享，跨 block 不能访问

## 六、纠偏：你不是"按硬件分 block"，是"在硬件约束下选 block 尺寸"

硬件约束：
1. block 线程上限 1024
2. block 大小最好 **32 的倍数**（warp 是 32，避免 partial warp 浪费算力）
3. 同时配合 tile 尺寸（tile=16×16=256 线程，刚好一个 block）

Block 尺寸是**调优旋钮**：既要适配 tile，也要让 SM 塞够多 warp 达到高**占用率（Occupancy）**——SM 里活跃 warp 占硬件最大可容纳 warp 的比例，是 CUDA 调优核心指标之一。

## 七、职责分开记忆表

| 概念 | 类型 | 谁管理 | 核心作用 |
| :--- | :--- | :--- | :--- |
| Kernel | 软件函数 | 你写 | GPU 任务入口 |
| Block | 软件抽象组 | 你定义，SM 承载 | 划定 shared 范围、同步域 `__syncthreads()` |
| Warp | 硬件执行单元 | GPU 自动打包 | 取指、发射、SIMT 执行，32 线程 |
| Tile | 数据分块策略 | 你在 kernel 里手写 | 调度 shared，减少全局显存访问 |
| SM | 硬件资源容器 | GPU 硬件 | 跑 block，有寄存器池、shared、L1、warp 调度器 |

## 八、经典踩坑串联：矩阵乘 tiled kernel

- 设 block = 16×16 = 256 线程（**软件**）
- 硬件自动打包成 8 个 warp（**硬件**）
- 代码里 `TILE_WIDTH=16`，一个 block 加载 16×16 的 A、B tile 进 shared（**数据策略**）
- block 内所有 warp 协作加载 tile，`__syncthreads()` 等全加载完再算
- 若 warp 内 if 分支不一样 → **warp divergence** → 性能下滑

## 九、极简总结

1. **Block**：软件分组，划定同步域和 shared 范围，必须落在单个 SM 上
2. **Warp**：硬件最小执行包，固定 32 线程，硬件自动打包，不能直接控制
3. **Tile**：与硬件调度无关，是数据搬运复用方案，放在 kernel 里
4. **日常开发流程**：写 kernel → 选 block 大小（对齐 warp、配合 tile）→ 在 block 内部写 tile 的加载、同步、计算逻辑

> 后续可深入：warp divergence（束发散）、warp shuffle（`__shfl_sync`，warp 内寄存器通信）——warp 最常考的优化点。
