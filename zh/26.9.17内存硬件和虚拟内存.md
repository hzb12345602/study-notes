# 26.9.17 内存：从硬件到虚拟内存

> 学习笔记。主线：物理内存（硬件）如何被抽象成虚拟内存，以及中间的翻译机制。
> 起点问题：指令 / 地址"不够用"，是不是就是位数不够？

## 一、起点：位数限制的是三件不同的事

一开始我以为是同一个问题，其实是三个维度：

| 限制类型 | 由什么决定 | 后果 |
| :--- | :--- | :--- |
| 指令种类不够 | 操作码(opcode)位数 | 最多 2^N 条指令，无法新增 |
| 地址空间不够 | 地址位数 | 最多访问 2^N 个单元（32位 → 4GB，16位 → 64KB） |
| 立即数范围不够 | 立即数字段位数 | 只能表示有限范围的常数 |

- RISC-V 的 opcode 占 7 位 → 最多 2⁷ = 128 条基础指令
- 混淆点：**指令本身也存在内存里**，每条指令占一个地址。所以地址位数少 → 程序能占的内存小 → 能放的指令也少。但这是"存储容量"限制，不是"编码种类"限制。

ISA 突破位数限制的技巧：
- **操作码扩展（转义码）**：先用一个操作码表示"这是扩展指令"，再用后续字段细分。x86 这么干，指令极多但解码复杂
- **变长指令**：RISC-V 32 位基础 + 16 位压缩 + 48/64 位扩展
- **寄存器间接寻址**：地址字段放不下 32 位地址，就只放寄存器编号
- **立即数分段加载**：放不下 32 位立即数，用 `lui` + `addi` 两条拼出来

## 二、物理内存本来的样子：一堆没有标签的页帧

这是理解虚拟内存的起点。

物理内存（DDR 颗粒）**不知道**什么是代码段、数据段、栈。它只是一大堆固定 4KB 的**页帧（Page Frame）**，像一叠白纸。操作系统维护一个**空闲页帧链表**，谁要内存就从链表摘一个。

关键：**物理内存没有被预先分区。** 同一个进程的代码段和栈，在物理上可能相隔很远、甚至不相邻。

## 三、虚拟地址空间：操作系统画的"分区地图"

程序运行时看到的不是物理内存，而是操作系统为每个进程画的一张**虚拟地址空间地图**，标好了哪段是代码、数据、堆、栈：

```text
高地址  ┌─────────────────┐
        │   内核空间       │  ← 用户程序不可访问
        ├─────────────────┤
        │   栈 (Stack)     │  ← 局部变量、返回地址，向下增长
        │       ↓          │
        ├─────────────────┤
        │       ↑          │
        │   堆 (Heap)      │  ← malloc/new，向上增长
        ├─────────────────┤
        │   .bss 段        │  ← 未初始化全局变量
        ├─────────────────┤
        │   .data 段       │  ← 已初始化全局变量
        ├─────────────────┤
        │   .text 段       │  ← 机器码指令
低地址  └─────────────────┘
```

这张地图是纯软件层面的**约定**，由操作系统和编译器共同"编"出来。

## 四、运行时：地址是怎么被"用"起来的

程序里的 PC、SP、指针值，**全都是虚拟地址**，没有一个是物理地址。

- **取指令**：PC 指向 .text 段某地址 → MMU 查页表 → 翻译成物理地址 → 取出 32 位指令
- **全局变量**：编译器把 `counter` 放在 .data 段固定虚拟地址，读写就是对该地址 load/store
- **函数调用**：SP 下移，压入返回地址和局部变量；返回时 SP 上移，地址被"释放"（数据还在，只是不再被引用）
- **动态分配**：`malloc(100)` 在堆区找一块空闲地址范围，返回起始地址

## 五、核心机制：虚拟地址 → 物理地址的翻译

```text
程序看到的虚拟地址：0x0800_1000
        ↓ MMU 查页表
物理内存实际地址：  0x2000_1000
```

页表把地址空间切成固定大小的**页**（通常 4KB），每页一个映射条目。操作系统改页表，就能控制：哪页可读 / 可写 / 可执行、哪页根本不在内存（触发**缺页中断**从磁盘加载）。

**是页表把"地图上的虚拟坐标"翻译成"物理页帧的真实位置"，让程序以为自己独占了一块连续、分区清晰的内存。**

## 六、对应 Linux 源码

- `struct mm_struct`：描述一个进程的整个地址空间
- `vm_area_struct`：描述地址空间里的一段（代码 / 数据 / 堆 / 栈各一个），含 vm_start、vm_end、权限
- `pgd_t / pmd_t / pte_t`：多级页表，逐级把虚拟地址翻成物理地址
- `do_page_fault()`：访问未映射地址时，CPU 触发缺页异常，内核在这里决定分配新页还是报 Segmentation Fault

## 七、关键对比：虚拟 vs 物理

| | 虚拟地址空间 | 物理内存 |
| :--- | :--- | :--- |
| 是否分区 | 是，人为划分成段 | 否，只是一堆页帧 |
| 谁管理 | 操作系统 + 编译器 | MMU 页表 + 内核页帧分配器 |
| 连续性 | 每段内部连续 | 不保证连续 |
| 可见性 | 程序看得见 | 程序看不见 |

## 八、用 FPGA 类比

- **虚拟地址空间** = Verilog 里的地址译码逻辑：规定 `0x0000_0000` 是 ROM、`0x1000_0000` 是 UART、`0x2000_0000` 是 DDR。这是人为约定的地址映射
- **物理内存** = 板子上那颗 DDR 颗粒：它不知道哪块是 ROM、哪块是 UART，只是被动接受地址总线和数据总线的读写
- **MMU** = 一个可编程的地址译码器，页表 = 它的译码表。操作系统改页表，就能随时改变映射关系

## 九、一句话总结

> 物理内存只是一堆没有标签的页帧；虚拟内存是操作系统给每个进程画的"分区地图"。是页表和 MMU 把地图上的虚拟坐标翻译成物理页帧的真实位置，让程序以为自己独占了一块连续、分区清晰的内存。
